# Release corelib-java

There is **no registry publish**. `pom.xml` has no `distributionManagement`, no
`maven-deploy`/`maven-gpg`/central-publishing plugin, and there is no release
workflow — CORELIB_PLAN §12 makes one optional ("a corelib that ships no package
has none"). A release here is: the version copies agree → a merge commit on
`main` → an annotated tag → a GitHub release. Never tell the user an artifact
landed on Maven Central.

**The git tag is the source of truth for the version.**
`.github/workflows/version-consistency.yaml` runs on `v*` tag pushes only and
fails the tag unless the `<project><version>` in `pom.xml` equals the tag minus
its leading `v`. It checks nothing else — every other copy below is on you.

## Where the version is written

| Place | What | Checked by CI? |
|---|---|---|
| `pom.xml` `<project><version>` | the only manifest in the repo | **yes** (on tag push) |
| `pom.xml` comment block above `<version>` | the in-place changelog: what this version breaks and why | no |
| `README.md` "Maven coordinates `org.sofabuffers:corelib` (version `X.Y.Z`)" | prose | no |
| `README.md` `<version>X.Y.Z</version>` in the dependency snippet | copy-pasteable POM | no |
| `Sofab.API_VERSION` | **wire** contract, not this artifact's version | no |

Check both README spots by hand — they have gone stale before
(`e65503a docs(readme): correct the stale artifact version (0.9.0 -> 0.10.0)`):

```bash
grep -nE '\b[0-9]+\.[0-9]+\.[0-9]+\b' README.md pom.xml | grep -v '<!--'
```

`Sofab.API_VERSION` tracks the bytes on the wire and is identical in every port
(CORELIB_PLAN §6.2). Its own javadoc settles it: "a release that renames or
removes a Java method bumps the artifact version in `pom.xml` and leaves
`API_VERSION` alone." **Only** bump it if the wire encoding changes meaning.

## Picking the number

- **Pre-1.0, the minor is where a breaking change lands** — API-source-breaking
  or wire/behaviour-breaking alike (stated in the `pom.xml` comment block).
  Patch releases exist for non-breaking fixes (`corelib-py` shipped `v0.10.1`).
- **The pom version is normally already ahead of the newest tag, and that is
  correct, not broken** (CORELIB_PLAN §12.3). In this repo the bump and its
  changelog note land in the *feature* PR that breaks things — `0.11.0`
  (#104), `0.12.0` (#105) and `0.13.0` each arrived that way. So the usual
  release has **nothing to bump**: you tag the number pom already carries.

```bash
git tag --sort=-v:refname | head -3
python3 -c 'import xml.etree.ElementTree as ET; print(ET.parse("pom.xml").getroot().find("{http://maven.apache.org/POM/4.0.0}version").text)'
```

- If pom == newest tag, this release *does* need a bump: raise the minor (or
  patch) and add the note to the comment block — newest version described in
  full at the top, the previous ones compressed into the parenthesised tail.
- Releases are family-wide alignments, so check where the siblings stand and say
  so in the notes:

```bash
for r in corelib-c-cpp corelib-cpp corelib-rs corelib-rs-no-std corelib-py corelib-ts corelib-go corelib-cs; do
  printf '%-20s ' "$r"; gh api "repos/sofa-buffers/$r/tags" -q '[.[].name][0:2]|join(" ")'
done
```

(`generator` versions independently — it was at `v0.23.0` while the corelibs sat
at `0.10.x`.)

## Procedure

**1. Preflight.** On `main`, clean, up to date, and green:

```bash
git status -sb && git pull -p
gh run list --branch main --limit 5
```

CI must be green on the release commit — `mvn -B verify` across JDK 17/21/25,
coverage badge > 90 %. Do not tag a red `main`.

**2. Vectors current.** `assets/test_vectors.json` is generated by
`corelib-c-cpp`; never hand-edit it. Confirm it matches upstream before tagging:

```bash
curl -sS https://raw.githubusercontent.com/sofa-buffers/corelib-c-cpp/refs/heads/main/assets/test_vectors.json \
  | diff -q - assets/test_vectors.json && echo "vectors in sync"
```

A drift means a conformance PR comes first, not a release.

**3. Local verification.**

```bash
mvn -B verify
mvn -q compile exec:java -Dexec.mainClass=org.sofabuffers.sofab.bench.Perf
mvn -q compile exec:java -Dexec.mainClass=org.sofabuffers.sofab.bench.Bench
```

Two BENCH_SPEC parity checks must hold, and they are cheap proof the encoder is
byte-correct: the `perf` message encodes to **170 bytes**, and `blob 1MB` to
**1,000,005 bytes**.

**4. The release PR** — only if something needed changing (a bump, or a stale
README). Otherwise skip to step 5 and tag the existing `main`.

```bash
git switch -c release/vX.Y.Z
# edit pom.xml <version> + comment block, README.md (both spots)
git commit -am 'chore(release): X.Y.Z'
gh pr create --title 'chore(release): X.Y.Z' --body '...'
```

That is exactly what `v0.10.0` did: branch `release/v0.10.0`, one commit
`chore(release): 0.10.0`, merged as a **merge commit** (PR #55), then tagged.
Keep the merge commit — the tags point at merge commits.

**5. Tag `main`.** Make it **annotated** (`v0.9.0` was, `v0.10.0` was not — the
annotated form is the one to keep):

```bash
git switch main && git pull -p
git tag -a vX.Y.Z -m 'SofaBuffers corelib X.Y.Z'
git push origin vX.Y.Z
```

**6. Watch the tag check.** The version-consistency run is the gate that proves
pom and tag agree:

```bash
gh run list --workflow version-consistency.yaml --limit 3
```

If it fails, **delete the tag** (`git push origin :refs/tags/vX.Y.Z`), fix the
version, and tag again — do not leave a red tag standing.

**7. GitHub release.**

```bash
gh release create vX.Y.Z --title vX.Y.Z --notes-file <notes.md>
```

## Release-notes shape

Follow `v0.10.0`'s: an alignment line, the breaking changes with their upstream
provenance, then the generator's state.

```markdown
Aligns this library with the rest of the SofaBuffers family at **X.Y.Z**. The git tag is the
source of truth for the version; every package manifest matches it.

**Breaking since vA.B.C** — under the pre-1.0 rule that a minor bump may break API or wire output:

- **Crucible F-00NN / CORELIB_PLAN §N.N** — what changed, and what a caller does about it.
- **CORELIB_PLAN §N.N** — ...

sofabgen changed in lockstep and is on `main`.
```

Cite the section (and the Crucible finding, when there is one) that forced each
change — that is how the family's notes read, and the `pom.xml` comment block
for the version being released already contains the wording to draw on.

## Never

- Never tag before `pom.xml`'s version equals the tag without its `v`.
- Never bump `Sofab.API_VERSION` for a Java-only source break.
- Never hand-edit `assets/test_vectors.json`.
- Never add version-consistency triggers on `main`/PRs — tag pushes only, by
  design (CORELIB_PLAN §12.3).
